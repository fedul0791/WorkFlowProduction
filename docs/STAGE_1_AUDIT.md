### 2. Docker Compose и сохранение данных

- Compose-конфигурация проходит `docker compose config --quiet`.
- PostgreSQL 18 публикует host port `5432`; backend `8001 → 8000`; frontend `3001 → 3000`.
- Backend ожидает `db` в состоянии healthy; frontend ожидает healthy backend.
- PostgreSQL хранит данные в именованном volume `postgres_data`, смонтированном в `/var/lib/postgresql` — корректная точка volume для официального образа PostgreSQL 18.
- Обычный `docker compose down` сохраняет volume. `docker compose down -v` удалит локальные данные.
- Текущее состояние: все три контейнера работают; PostgreSQL и backend отмечены healthy. Frontend проверен прямым HTTP-запросом.

**Риск:** публикация `5432:5432`, `8001:8000` и `3001:3000` без host-IP означает привязку к `0.0.0.0`, а не только loopback. При включённом Docker Desktop эти порты могут быть доступны с других устройств в сети. Особенно чувствителен опубликованный PostgreSQL с общей dev-конфигурацией.

### 3. Конфигурация и секреты

- Корневой `.env` отсутствует.
- `.env.example` содержит только пример локальной конфигурации и предсказуемое dev-значение пароля; реального секрета в проверенных файлах не найдено.
- `.gitignore` исключает `.env` и `.env.*`, затем явно разрешает `.env.example`.
- Docker Compose автоматически не загружает `.env.example`. Источники интерполяции Compose: переменные окружения процесса, файл `.env` в каталоге проекта (если создан) и значения `:-...` по умолчанию в Compose. `.env.example` вступит в действие только после копирования в `.env`.
- В контейнер передаётся `DATABASE_URL`; Pydantic Settings сначала учитывает переменные окружения контейнера и лишь затем настроенный `env_file`. В текущем Compose environment задаётся явно.
- По выводу Git, индекс пуст, истории коммитов нет. Поэтому фактически закоммиченных секретов нет; все файлы пока untracked. Credential-подобное значение — только явно обозначенный локальный placeholder в dev-конфигурации.

**Риск:** Compose содержит значения по умолчанию для БД, включая предсказуемые локальные реквизиты. Это допустимо только для изолированной разработки. В сочетании с опубликованным на `0.0.0.0` портом БД такие значения не следует использовать в общей сети или production.

### 4. Backend, PostgreSQL и OpenAPI

- `/health` выполняет `SELECT 1` через SQLAlchemy и возвращает `{"status":"ok","database":"connected"}` при доступной БД.
- При исключении подключения route возвращает HTTP 503 с общим сообщением `database: unavailable`; текст исходного исключения не включён в JSON-ответ.
- SQLAlchemy engine создаётся из `DATABASE_URL` с `pool_pre_ping=True`.
- OpenAPI содержит только маршрут `/health`; `/docs` отвечает `200`.
- CORS middleware и явные CORS origins отсутствуют. Сейчас frontend не вызывает API, поэтому это не блокирует текущий процесс. Перед браузерной интеграцией нужно определить разрешённый origin, а не включать wildcard без необходимости.
- Аутентификации и административных маршрутов нет. Открытая документация API сейчас описывает только health endpoint.

### 5. Alembic и миграция `0001_infrastructure`

Файл миграции имеет пустые `upgrade()` и `downgrade()`. Он сам не создаёт бизнес-таблиц. Alembic создал служебную `public.alembic_version` и записал текущую ревизию `0001_infrastructure`.

Повторный `alembic upgrade head` по коду и состоянию Alembic должен быть no-op: текущая версия уже равна `head`, а ревизия отмечена применённой. Повторный запуск в рамках аудита не выполнялся, чтобы не менять состояние БД. При старте backend эта команда вызывается перед Uvicorn.

- Переключатель языка ведёт на существующие локализованные маршруты. Бренд и пункт «Обзор» ведут на текущую локаль.

**Замечание по доступности:** корневой `<html>` всегда получает `lang="de"`, а содержимое страниц `/ru` и `/en` размечено вложенным `div lang=...`. Большинство содержимого наследует правильный язык от вложенного элемента, но язык всего документа остаётся немецким. Перед полноценной локализованной эксплуатацией лучше задавать `html lang` на уровне маршрута.

## Найденные ошибки и риски

| Приоритет | Наблюдение | Последствие |
|---|---|---|
| Высокий перед запуском в общей сети | Compose публикует БД и приложение на `0.0.0.0`; БД использует известные dev defaults | Доступ к локальной БД и endpoints из локальной сети; недопустимо для общей/производственной среды |
| Средний | README в разделе проверки указывает `http://localhost:8000/health`, тогда Compose публикует API на host port `8001` | Документированная проверка на Windows по этой команде не попадёт в запущенный Compose backend |
| Средний, для будущей локализации | `html lang="de"` зафиксирован для страниц всех языков | Семантика языка всего документа неправильна на RU/EN страницах |
| Низкий, перед интеграцией frontend с API | CORS не настроен | Браузерные запросы с frontend origin на отдельный backend port будут блокироваться браузером, пока origins не будут согласованы |
| Будущее production hardening | `/docs` и `/openapi.json` открыты; TLS/auth отсутствуют; контейнеры предназначены для development | Перед развёртыванием вне локальной машины потребуются отдельные production настройки |

Найденных проблем с миграцией, подключением к PostgreSQL, повторной обработкой статуса Alembic или существующими frontend-ссылками не выявлено.

## Рекомендуемые действия до следующего этапа

1. Согласовать ограничение публикации портов loopback-only и убрать доступность PostgreSQL из локальной сети; не использовать dev defaults вне изолированного компьютера.
2. Исправить команду health check в README на фактический host port `8001`.
3. При переходе к дальнейшей локализации перенести `lang` на уровень документа для каждого языка.
4. До первого browser-to-API запроса определить allowlist CORS origins и добавить его вместе с клиентом API.
5. До production-развёртывания отдельно согласовать аутентификацию, закрытие/ограничение Swagger, TLS и production secrets.
